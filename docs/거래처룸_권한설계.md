# 아미코진스 거래처룸 — 접근 권한·보안 설계 v0.1

작성 2026-08-21 · DYBROS Co.
전제: [02_거래처룸_워크플로_설계]의 오더 카드 구조 위에 권한 계층을 얹는다.

---

## 0. 원칙 하나

**"화면에서 안 보이게"는 보안이 아니다.** 브라우저 개발자도구를 열면 숨긴 값이 그대로 보인다.
권한은 **DB의 행(row) 단위**에서 막는다. 프론트에서 감추는 것은 편의이지 방어가 아니다.

이 원칙에서 두 가지가 따라온다.
- 원가·공장명은 오더 테이블에 **같이 두지 않는다.** 별도 테이블로 쪼개고, 거래처 계정에는 그 테이블의 조회 권한을 아예 주지 않는다.
- 사진·파일은 공개 버킷에 두지 않는다. 비공개 버킷 + 서명 URL(만료 있는 임시 주소)로만 내보낸다.

## 1. 사이트를 두 채로 나눈다

```
공개 사이트                        거래처룸 (로그인)
GitHub Pages · 정적               Vercel + Supabase
────────────────────              ─────────────────────
컬렉션 · 프로젝트 · 브랜드         오더 카드 · 사진 · 파일
누구나 열람                        인증된 계정만 · RLS로 행 단위 차단
DB 없음                            DB 있음 (T2)
```

같은 도메인 아래 `amicojeans.com` / `amicojeans.com/room` 으로 붙이되, **배포와 저장소를 분리**한다.
공개 사이트가 뚫려도 거래처 데이터에 닿지 않고, 거래처룸을 고칠 때 공개 사이트를 건드리지 않는다.

스택은 dybros-app에서 이미 검증된 것을 그대로 쓴다 — Supabase(Postgres + Auth + Storage) + Vercel.
새로 배울 것도, 새로 뚫릴 곳도 없다.

## 2. 접근 레벨 4단계

| 레벨 | 누구 | 보는 범위 | 쓰기 |
|---|---|---|---|
| `owner` | 남상백 대표 | 전체 오더 · 원가 · 공장 · 계정 관리 | 전부 |
| `staff` | 아미코 직원 | 담당 거래처 오더 전부 · 원가 | 상태 변경 · 사진 · 코멘트 |
| `client` | 거래처 담당자 | **자기 회사 오더만** · 원가/공장 차단 | 코멘트 · 확인 · 예약 |
| `guest` | 비로그인 | 공개 사이트만 | 없음 |

거래처 담당자가 여러 명일 수 있으므로 계정은 **사람 단위**, 권한은 **회사 단위**로 건다.
퇴사·교체는 `profiles.active = false` 한 줄로 즉시 회수된다.

## 3. 테이블 — 민감한 것은 애초에 떼어 놓는다

```
companies      거래처 회사        id, name, active
profiles       계정               user_id, role, company_id, active
orders         오더 카드          id, company_id, staff_id, style, stage, qty, due
order_costs    원가·공장  ★분리   order_id, unit_cost, factory_id, margin
factories      공장 정보  ★분리   id, name, region, contact
order_events   사진·코멘트        order_id, kind, body, file_path, visibility
access_log     조회 기록          user_id, order_id, at, action
```

★ 표시 두 테이블이 이 설계의 핵심이다. 거래처가 절대 봐서는 안 되는 값(단가·마진·공장명)은
`orders`에 컬럼으로 붙이지 않는다. 같은 테이블에 두면 실수 한 번(SELECT *)에 전부 새어 나간다.

`order_events.visibility` 는 `internal` / `client` 두 값. 공장에서 온 사진 중 무엇을 거래처에 보일지
직원이 고른다. 기본값은 `internal` — **실수로 열리는 쪽이 아니라 실수로 닫히는 쪽**이 안전하다.

## 4. RLS — 권한을 DB에 새긴다

Supabase의 Row Level Security를 켜면, 어떤 경로로 접근하든 정책을 통과한 행만 나온다.
프론트 코드가 잘못돼도 데이터는 안 샌다.

```sql
alter table orders enable row level security;

-- 거래처: 자기 회사 오더만
create policy client_own_orders on orders for select
using (
  company_id = (select company_id from profiles
                where user_id = auth.uid() and active)
);

-- 직원·대표: 전체
create policy staff_all_orders on orders for select
using (
  (select role from profiles where user_id = auth.uid() and active)
  in ('owner','staff')
);

-- 원가 테이블: 거래처 정책을 아예 만들지 않는다 (= 조회 불가)
alter table order_costs enable row level security;
create policy staff_only_costs on order_costs for all
using (
  (select role from profiles where user_id = auth.uid() and active)
  in ('owner','staff')
);
```

정책이 없는 테이블은 RLS가 켜진 순간 **아무도 못 읽는다**. 이 기본값이 우리 편이다.

## 5. 로그인 방식 — 비밀번호를 만들지 않는다

거래처 담당자에게 비밀번호를 만들게 하면 반드시 잊어버리고, 그 순간 카톡으로 돌아간다.
**이메일 매직링크**(메일로 온 링크 클릭하면 로그인)로 간다. 외울 것이 없고, 메일함을 잃지 않는 한 안전하다.

- 초대는 대표·직원이 관리 화면에서 이메일을 넣으면 발송
- 링크 유효 시간은 짧게(기본 1시간), 세션은 길게(재로그인 잦으면 안 씀)
- 계정 회수는 `active = false` — 링크가 살아 있어도 정책에서 걸린다

## 6. 사진·파일

비공개 버킷에 `company_id/order_id/파일명` 경로로 저장하고, 화면에 보일 때만 **만료 있는 서명 URL**을 발급한다.
주소를 복사해 밖으로 돌려도 시간이 지나면 죽는다. 버킷 자체에는 RLS와 같은 경로 정책을 건다.

## 7. 남는 기록

원가 조회, 오더 열람, 파일 다운로드는 `access_log`에 남긴다. 사고가 났을 때
"누가 언제 무엇을 봤는가"에 답할 수 있어야 거래처에 설명이 된다.

## 8. 도입 순서 — 위험한 것을 마지막에

| 단계 | 붙이는 것 | DB | 위험도 |
|---|---|---|---|
| 1 | 공개 사이트 (지금) | 없음 | T0 |
| 2 | 로그인 + **읽기 전용** 오더 조회 (거래처 1곳 시범) | 있음 | T2 |
| 3 | 사진·코멘트 쓰기, 상태 변경 | 있음 | T2 |
| 4 | 오더 카드 → 컬렉션 공개 연동 | 있음 | T1 |

2단계에서 읽기만 여는 이유: 권한 설계가 틀렸을 때 **잘못 보이는 것**은 고칠 수 있지만
**잘못 써진 것**은 되돌리기 어렵다. 한 시즌 읽기로 돌려 보고 쓰기를 연다.

## 9. DYLOOM 관점의 T2 재정의

아미코 저장소에서 아래를 건드리는 변경은 자동 머지 경로에서 빼낸다(사람 세션이 받는다).

- `supabase/**.sql` · RLS 정책 · 마이그레이션
- 인증 경로 · 세션 · `profiles` 의 role/company_id
- `order_costs` · `factories` · 단가·마진 관련 표현
- 대외 공개 정보(대표 이력·쇼룸 주소·중국 사무소·거래처명)
- `.github/workflows/**` · 도메인 · 환경변수

나머지(공개 사이트 문구·레이아웃·사진 교체·컬렉션 카드)는 T0/T1으로 자동 처리한다.
